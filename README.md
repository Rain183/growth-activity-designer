# growth-activity-designer · 用增活动设计 Skill

> 把一个模糊的业务诉求，变成一份能直接进评审会的完整用增活动方案——**且过程中不许跳步、不许糊弄**。
>
> 这是一个把「超市用增活动怎么设计」的完整方法论装进 AI 的 skill：从一句诉求出发，按 **S1–S8** 分步推演，产出可评审的产品方案（活动规则 / 逆向风控 / 曝光动线 / 成本与实验 / 决策点汇报表）+ 一份可直接投屏的 HTML 评审报告。

---

## 它解决什么问题

用增活动方案依赖一整套方法论思考框架，形成一个完备方案约 **15 人日**，而方法论**内隐在少数资深产品脑中**——产能瓶颈的本质是方法论没有被资产化。

这个项目做的事：**把资深产品经理的隐性推演顺序，显性化成一款可复用、可验证、有质量门禁的 skill。**

关键洞察是：一开始把全部文档投喂给 AI，三次跑出三个样子。问题不在提示词，而在于——**方法论是「要考虑什么」的内容清单，不是「先想什么后想什么」的操作流程。顺序不在文档里，在老产品经理的工作过程里。**

---

## 三个核心机制

### 1. 门禁脚本：防跳步、防糊弄（硬停）

每一步的产物必须命中规定要素才准放行，否则**状态不落账、流程硬停**：

```console
$ python3 scripts/ledger.py advance ../runs/某活动 S3
❌ ledger：防跳步：前序未完成 ['S1', 'S2']
```

这不是报错，是哨兵在站岗——**方案不是一次生成出来的，是被八道关卡卡出来的。**

### 2. 生产台账：状态即资产

`ledger.json` 是任务状态的**唯一权威源**：一切状态读写经脚本、产物哈希入账、改了跑 `diff` 立刻暴露。一次会话中断不会再丢掉推演进度。

### 3. 边界设计：判断权留给人

skill 只产出到**可评审的产品方案**为止——不往下出 PRD 级需求文档与系统设计，不碰预算（额度与归属是业务方职权）。所有需要拍板的判断单独成表：

> **决策点汇报表**：把「我定的」和「请业务/风控/客服拍板的」分开列。

**AI 负责推演完备，人负责关键判断。**

## 能力范围（S1–S8）

| 步 | 动作 | 产物 | 门禁 |
|----|------|------|------|
| S1 | 诉求澄清：只问业务四问 | 活动画像（北极星+护栏+人群+资源+底线） | `check_brief.py` |
| S2 | 信息装载：按信息量地图定位信息件，动态数据生成取数清单 | 信息底座（逐条标注来源与时点） | `check_context.py` |
| S3 | 玩法选型与规则设计：指标倒查玩法库→触发规则结构化→互斥扫描 | 活动规则（四字段带口径+杠杆参数进实验位） | `check_rules.py` |
| S4 | 逆向与风控：五场景逐项过 + 结构性判据 | 逆向方案（含硬停否决） | `check_reverse.py` |
| S5 | 曝光动线：触点×用户状态矩阵 | 曝光动线（含红线标注） | 并入 `check_experiment` |
| S6 | 成本与实验：成本公式化 + 实验点盘点 + 分轮计划 | 成本与实验 | `check_experiment.py` |
| S7 | 方案汇编与审查（生成与审查分离） | 产品方案 + 决策点汇报表 + 审查报告 | `check_final.py` |
| S8 | 方案可视化（代码渲染，不改内容） | 可投屏 HTML 报告 | `render_report.py` |

## 怎么验证它可靠：预埋标准答案盲测

「自己跑几次感觉挺稳」不是验收。验收要有标准答案：

**找一个已被市场验证过的真实活动，只把它当年的原始业务诉求喂给 skill，跑完全流程出方案，与线上真实设计逐模块对照判分。**

三个活动三种角色，**测与学不能互串**：

| 活动 | 角色 | 为什么 |
|---|---|---|
| 满额返超市卡 | 教学案例 | 方法论从它提炼，考它等于开卷 |
| 超市卡消费挑战 | 真实生产场景 | 有人工校验兜底 |
| 每天来抽卡 | **封存的盲测标准答案** | 概率型成本结构是前两者都没有的考点——测的是方法论泛化，不是背案例 |

**防泄漏纪律**：盲测执行期间，`examples` 与 `playbooks` 均**不含任何概率型日频条目**——否则就是"先看了答案再考试"。概率型玩法条目（`p6`）是**判分完成后**才回流入库的（见其文件头标注的入档时间）。

**盲测结果：要素命中 15/18 ≈ 83%，逆向场景覆盖 5/5。**

有价值的不是命中率，是**漏项归因**：3 个漏项全部集中在概率型运行时保护机制——玩法库中无概率型先例，方法论推出了「要控成本」，推不出「怎么在运行时控」。漏项已回流进玩法库（`references/playbooks/p6-每日概率抽奖型.md`）。

> **盲测暴露的真实边界，比命中率本身更值钱——因为边界是可以补的。**

## 快速上手（仅需 Python 3.8+，Win/Mac 通用）

1. **看一次完整运行**：浏览器直接打开 `runs/消费挑战/10-方案可视化.html`（一页纸评审要点 + 完整方案分节展开，覆盖 S1–S7 产物），再对照同目录 `01-…` 到 `09-…` 逐份看每步产物；**上线后的实验判读与定档另见 `11-实验判读与定档.md`**（它在 S8 之后产生，不参与渲染）。

2. **体验门禁**：进入 skill 目录，试试防跳步——
   ```console
   cd growth-activity-designer
   python3 scripts/ledger.py status "../runs/消费挑战"
   ```

3. **跑一个新任务**：把 `test-scenarios.md` 里的诉求（或自拟一句业务诉求）交给你的 AI 助手，让它按 `SKILL.md` 的路由推进；S2 索要数据时，把 `mock数据/` 目录路径给它装载。全流程可离线跑通。

## 数据口径声明

本仓库是**脱敏演示资产包**：不连接任何内部系统，`mock数据/` 是按真实来源系统结构重建的模拟样本，**其数值与项目交付的真实数字不同**（真实口径以项目交付物为准）。

因此，仓库内数字只保证**本沙盒内部自洽**（先例锚点、判读结果、实验设计三处同源），与真实项目结果不作一致性要求。本包用于完整跑通并展示流程。

## 边界声明

### 一、刻意选择：只到可评审方案为止

skill 的产出**只到「可评审的产品方案」**——不往下出 PRD 级需求文档与系统设计。这是刻意切的一刀：

> 方案是能独立评审的完整交付物，切在这里就天然留出了人的拍板位：请示项单独拎成决策点汇报表。**AI 负责推演完备，人负责关键判断。**

同一条边界也解释了另外两件事：**上线后验收方式**是项目验收职责、**预算管理**（额度与归属）是业务方职权——均越界，不进 skill。

### 二、已知能力边界

真正的能力缺口只有一类，且已被修补——这里把它和"刻意不做"分开列，避免混淆：

| 边界 | 性质 | 现状 |
|---|---|---|
| **运行时保护机制**（如概率型的日奖池封顶降档） | **真缺口**：方法论的泛化边界 | 玩法库中无概率型先例时，方法论**推出了「要控成本」，推不出「怎么在运行时控」**——该漏项已回流补进玩法库（`references/playbooks/p6-每日概率抽奖型.md`）。**不是原生能力，是盲测暴露后补齐的** |
| **系统流程图与系统需求** | 刻意不做：业务分工 | 不在产出范围，由研发与相关系统产品承接（见 `references/templates/方案模板.md` 边界声明） |
| **动态数值本身** | 刻意不做：架构选择 | 数值会过期、口径不会——信息量地图只存**取数口径与获取路径**、不存数值；当期数值由 S2 按口径向系统/使用者索取 |

> **边界是可以补的**：盲测的价值不在于证明它已经完美，而在于把边界暴露出来——暴露一条、回流一条。同类边界肯定还有，这正是验收必须用封存的真实活动盲测、而不是"自己跑几次感觉挺稳"的原因。
